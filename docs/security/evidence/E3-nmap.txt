## Análisis de los resultados

| Hallazgo | Análisis | Acción |
|---|---|---|
| 80 y 443: nginx, sin versión | `server_tokens off` oculta la versión (banner grabbing mitigado). 80 solo redirige a HTTPS | Ninguna |
| 8000 (backend) y 1025 (SMTP de Mailpit): cerrados | Backend, base de datos y Mailpit están en redes internas de Docker sin puertos publicados: solo Nginx es alcanzable (zona DMZ, denegar por defecto) | Ninguna |
| 8025 abierto | En Windows escucha solo en 127.0.0.1 (proxy TLS de Mailpit con Basic Auth). Nmap llega porque escanea desde dentro de la red virtual de Docker; desde la LAN no es accesible | Ninguna |
| 3306 (MySQL 9.3.0) y 5432 (PostgreSQL) abiertos | **No pertenecen a SecureFin**: son servicios instalados en el Windows del equipo (mysqld y postgres), escuchando en todas las interfaces. Exposición del equipo, no de la aplicación | Detenerlos o filtrarlos con el firewall de Windows antes de la demo |
| CVE-2011-3192 "VULNERABLE" en 443 | **Falso positivo de producto** (es un fallo de Apache), pero el script lo detecta porque Nginx devolvía `206 multipart/byteranges` con 11 rangos disjuntos: amplificación útil para un DoS | **Corregido** con `max_ranges 1;` en nginx.conf. Verificado abajo |
| XSS / CSRF (http-stored-xss, http-dombased-xss, http-csrf) | Sin hallazgos (CSP estricta, CSRF obligatorio en la API) | Ninguna |

## Verificación tras la corrección (max_ranges 1)
$ docker run --rm instrumentisto/nmap:7.95 -Pn -p 443 --script http-vuln-cve2011-3192 host.docker.internal
443/tcp open  https
(sin salida "VULNERABLE": el script ya no detecta la condición)
$ curl -I -H "Range: bytes=0-0,2-2,...,20-20" https://127.0.0.1/assets/<js>   → HTTP/1.1 200 OK (antes: 206 multipart/byteranges)
$ curl -I -H "Range: bytes=0-99"            https://127.0.0.1/assets/<js>   → HTTP/1.1 206 Partial Content (un rango sigue funcionando)
